# 重复启动修复（0.5.1）

2026-09-14。用户重复执行 Start-AutoCodex.ps1 及带 ExecutionPolicy Bypass 的启动命令，均收到笼统“服务启动失败”。日志实际原因是同一数据目录已由进程 42132 占用；该进程的 0.5.0 面板和认证接口正常。这是启动器没有复用后台实例，不是 PowerShell 执行策略问题。

## 行为要求

- 同一数据目录已有正常服务时，重新运行启动器应成功返回，并打开原面板；不重启服务、不重复创建任务、不清除数据库或锁。
- 只有数据目录锁的进程仍存在、连接文件对应同一进程、本机 HTTP 健康检查及管理口令认证均通过，才判为可复用。过期连接文件、另一模式的服务、端口上的其他程序不能误认。
- 默认启动重开原地址；明确指定不同端口、模式或 Codex 路径时，说明需要停止旧服务后重新启动，不静默忽略用户参数。
- 同时启动或旧服务正在启动时，限时等待并识别胜出的实例；活进程无响应时不删除锁或强行结束进程。
- 真正失败展示本次启动的具体原因及日志位置；端口占用提供可操作的端口提示。日志口令脱敏，不显示连接 token。
- 保留 NoBrowser、Foreground、CheckCodex、自定义数据目录、中文/空格路径和解压发布包行为。前台重复启动也重开已运行实例；首次前台启动保留当前工作方式。

## 实现方案

把后台派生和就绪确认合并到 Node 启动助手：启动前检查原实例，派生后等待认证就绪，竞争失败后再次识别原实例。PowerShell 负责参数、插件配置与打开浏览器，不再仅凭子进程退出给出通用错误。后台配置在确认实例可用后生成。

服务身份检查限定 127.0.0.1 的合法 HTTP origin，禁止重定向；管理接口返回值只用于核对，不输出凭据。沿用已有连接格式及认证接口，因此能重开仍在运行的 0.5.0 服务。返回值只有状态、PID、地址和不含口令的文件路径。

## 验证计划

隔离数据目录验证：首次启动、重复启动、并发启动、旧连接残留、活锁但服务无响应、端口冲突、模式/参数冲突、认证错误、NoBrowser 与 Foreground 复用。核对重复启动保持同一 PID、任务和设置；实际 PowerShell 5.1 调用两种用户启动方式。验证发布包解压启动和本机现有实例重开，保存结果后提交并同步远程。
